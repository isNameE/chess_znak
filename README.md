# Контур производства

Демонстрационный производственный АРМ для общего стола агрегации двух линий маслозавода. Версия 0.3 построена вокруг смен, заданий, фактического состава, контроля этикеток и обработки нештатных ситуаций. Расчётный ориентир заказчика — 20–30 паллет за 8 часов.

Программа сохраняет границы нового ТЗ: существующие GPS Track & Trace, MySQL поставщика и оборудование линии розлива не изменяются. Камера, принтер и ответы учебной очереди пока имитируются. Реальные идентификаторы упаковок и приёмка ГИС МТ требуют отдельного согласования и испытаний.

## Что изменилось

- Обзор двух линий, текущая смена, план/факт заданий, фактический выпуск и инциденты.
- Производственные задания с линией, партией, продуктом и неизменяемым рецептом; запуск, пауза, продолжение, изменение плана с причиной и завершение.
- Короб формируется из конкретных кодов; паллета — из конкретных коробов. Контрольное считывание этикетки учитывается отдельно от открытия макета.
- Карантин, локальная разборка свободного короба до принятия/неопределённой отправки, сохранение истории состава и контролируемое устранение инцидентов.
- Персональные роли оператора, мастера и администратора; серверные сессии и журнал действий.
- PostgreSQL с ограничениями целостности, миграциями и индексами. Основной интерфейс получает текущую сборку и страницы по 25 записей вместо полного архива.
- Отчёты по датам и линиям, итоги смен и CSV. Хранится счётчик состава, отчёту не требуется загружать все бутылочные коды.
- Сохраняемая очередь, отдельный учебный фоновый обработчик, блокировка автоматического повтора при неопределённом результате. Подготовленный адаптер sandbox True API сохранён.

Изучены публичные решения Клеверенс, GPS, Квантрон и SmartPack. [Исследование, расчёт нагрузки и архитектура](docs/industrial-design.md) объясняют, что использовано и какие ограничения остаются. Код и интерфейс разработаны самостоятельно.

## Запуск на Windows

На серверном компьютере нужны 64-разрядный Python 3.13 и PostgreSQL 18. Моноблок клиента использует браузер; Python, PostgreSQL и обработка изображений на нём не нужны.

```powershell
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements-lock.txt
.venv/Scripts/python.exe scripts/setup_local_postgres.py
.venv/Scripts/python.exe server.py
```

Открыть [демо](http://127.0.0.1:8765). При следующих запусках — `Запустить демо.cmd`. Приложение останавливается Ctrl+C в окне сервера. Для собственного кластера помощник использует только `data/pg18`, порт 55432 и базу `arm_demo`; системная служба PostgreSQL и другие базы не изменяются. Локальный пароль генерируется в игнорируемом `.env`, кластер использует SCRAM и слушает loopback.

Для существующего сервера PostgreSQL скопировать `.env.example` в `.env`, настроить `DATABASE_URL` и запускать приложение без помощника кластера. Миграции применяются при старте; для первого запуска нужны права создания объектов. На заводе следует разделить учётные записи миграций и приложения, настроить HTTPS и резервное копирование.

`compose.yaml` — альтернативная PostgreSQL в Docker. В `.env` задать `POSTGRES_PASSWORD` и соответствующий `DATABASE_URL`, затем `docker compose up -d db`. Не использовать Docker и собственный кластер на одном порту одновременно.

## Демонстрация процесса

1. Открыть смену в разделе «Смены».
2. Создать задание: линия, продукция, партия, число полных паллет. Запустить задание.
3. На рабочем месте считать учебный кадр, проверить ошибки, закрыть короб.
4. Открыть макет, проверить совпадение контрольного идентификатора. Только проверенный короб доступен для паллеты.
5. Добавить короба и закрыть паллету. Для быстрого сценария мастер может смоделировать недостающие короба.
6. Проверить очередь, отказ, тайм-аут, сбой печати и инциденты. Состояние ошибки нельзя скрыть закрытием инцидента до устранения причины.
7. Проверить карточку вложенности, карантин и допустимую локальную разборку. Принятый/неопределённый документ не допускает разборки.
8. Завершить задание, закрыть смену, сформировать отчёт и CSV.

[Руководство оператора и мастера](docs/operator-guide.md).

Для начального показа можно явно создать учебную смену, два задания суммарно на 30 паллет и одну смоделированную паллету:

```powershell
.venv/Scripts/python.exe scripts/seed_plant_demo.py --with-pallet
```

Скрипт отказывается работать при существующих производственных заданиях и не заменяет реальные данные. При переносе из версии 0.2 прежние упаковки остаются в реестре с пометкой отсутствия задания/смены; они не присваиваются новым заданиям задним числом.

## Персональный доступ

По умолчанию `ARM_DEMO_MODE=true`: только loopback получает явно обозначенный административный демо доступ. Для проверки персональных ролей создать пользователей и выключить демо режим:

```powershell
.venv/Scripts/python.exe scripts/create_user.py operator1 --name "Оператор 1" --role operator
.venv/Scripts/python.exe scripts/create_user.py supervisor1 --name "Мастер смены" --role supervisor
```

Пароль вводится интерактивно, не передаётся аргументом и хранится как солёный PBKDF2-хеш. Установить `ARM_DEMO_MODE=false` в `.env` и перезапустить приложение. Учётная запись `demo-operator` не имеет пароля и не предоставляет персональный вход. Сессии действуют до 12 часов; роли и активность проверяются сервером на запросах.

Для сетевого показа дополнительно настроить `ARM_HOST`, общий защитный шлюз `ARM_ACCESS_USER`/`ARM_ACCESS_PASSWORD`, HTTPS через обратный прокси и доступ только из нужной сети. Это не заменяет персональные учётные записи. Сохранить Host и корректную схему при проксировании. Не публиковать PostgreSQL в клиентскую сеть. Перед производственной установкой проверить политику паролей, сертификаты, время, доступ ИТ-службы и сетевые ограничения.

## Обмен

На экране обмена явно показан имитатор. Отдельный процесс может обрабатывать только готовые учебные документы:

```powershell
.venv/Scripts/python.exe scripts/run_exchange_simulator.py
.venv/Scripts/python.exe scripts/run_exchange_simulator.py --loop --interval 5
```

Без `--loop` обрабатывается одна пачка до 100 документов. Сервис показывает heartbeat, не меняет версию рабочего места при пустых опросах, соблюдает контроль этикетки, карантин и зависимость паллеты от коробов. Реальные документы с провайдером `sandbox` не обрабатываются имитатором.

Настоящий True API по умолчанию выключен. Доступа и тестового сертификата пока нет. [Инструкция подключения](docs/true-api.md): авторизация внешней подписью, чтение КИ, транспорт подписанного документа. Тип упаковки, JSON-схема, товарная группа и методы сверяются по актуальной документации участника. `DEMO-*` отправлять в ГИС МТ запрещено. HTTP 200 и ID документа не подтверждают итогового принятия.

## Сохранение и резервные копии

```powershell
.venv/Scripts/python.exe scripts/backup.py
```

Custom-format дамп создаётся в игнорируемой папке `backups`; пароль передаётся `pg_dump` окружением. Восстановление проверять в новой отдельной базе через `pg_restore --no-owner --dbname=NEW_DATABASE backups/FILE.dump` с локально настроенными PGHOST/PGPORT/PGUSER/PGPASSWORD. Сверять упаковки, составы, задания, смены, документы и аудит; действующую базу автоматически не удалять.

Старый импорт `migrate_legacy.py data/demo.sqlite3` открывает SQLite только для чтения и разрешён в пустую базу. В текущем приложении SQLite не используется. Перед импортом в существующий производственный контур требуется отдельный план переноса, а не повтор начального импорта.

## Проверки и объём

```powershell
.venv/Scripts/python.exe -m pytest
node --check static/plant.js
.venv/Scripts/python.exe scripts/benchmark_plant.py --boxes 45000
```

Тесты создают случайные изолированные схемы и не очищают рабочие таблицы. Проверяются сквозная смена, задания, фактический состав, контроль этикетки, карантин, разборка, неопределённая отправка, повторные запросы, повтор кадров, конкурентное включение кода, персональные роли, CSV и пагинация. True API проверяется тестовым HTTP-транспортом без настоящего кабинета.

Объёмный тест создаёт 675 000 бутылочных кодов, 45 000 коробов и 900 паллет — расчётный максимум за 30 дней. Измеряет обзор, страницу реестра, поиск паллеты по бутылке и карточку состава; удаляет только собственную временную схему. Отчёт хранится в `data/benchmark-plant.json`. Это тест синтетического архива на машине разработки, не подтверждение аппаратной скорости, непрерывной сменной работы или трёхлетнего архива. Обнаруженный предел advisory-блокировок устранён миграцией с блокировками строк.

## Основные файлы

- `plant.py`, `plant_api.py` — производственные операции и ограниченный по объёму SQL API.
- `access.py` — персональные сессии и пароли.
- `migrations/` — история структуры PostgreSQL; старые миграции не заменяются сбросом базы.
- `static/plant.js`, `static/plant.css` — текущий интерфейс без npm-сборки, CDN и внешних шрифтов.
- `integrations/` — отдельный транспорт настоящего sandbox True API.
- `scripts/` — установка, демо, учётные записи, резервная копия, тест объёма и учебный сервис обмена.
- `repository.py`, `domain.py`, `static/app.js` — совместимость и история прототипа 0.2. Основной интерфейс не загружает его снимок истории. После начала смен старые команды отключены.

Базы, журналы, `.env`, дампы, ключи, сертификаты и локальные отчёты исключены из Git. Подключение оборудования, генерация настоящих КИГУ/КИТУ/SSCC, приёмка True API, промышленный мониторинг и SLA 99% остаются отдельными этапами испытаний и внедрения. Исходники не заменяют передачу прав по договору; сторонние библиотеки сохраняют свои лицензии.
