# Подготовка подключения True API

В этой версии подготовлен транспорт тестового контура. Подключение к настоящему кабинету и обработка настоящих документов не проверялись: доступ и тестовый сертификат пока не предоставлены. По умолчанию `TRUE_API_ENABLED=false`. Промышленный контур в приложении отсутствует.

## Что получить у предприятия

- Регистрацию и права в демонстрационном контуре для нужной товарной группы.
- Рабочий тестовый сертификат, криптопровайдер и средство CMS/CAdES-подписи на доверенном компьютере; при необходимости МЧД.
- Актуальную документацию True API из личного кабинета, методы формирования упаковок, JSON-схемы и допустимые идентификаторы.
- Тестовые GTIN и КИ нужного участника с подходящими статусами.
- Подтверждение типа упаковки: название «короб» само по себе не означает КИГУ.

Закрытые ключи, PIN, пароли и файлы сертификатов не передаются в чат и не коммитятся. Реальный криптопровайдер и сертификат могут требовать отдельной лицензии и установки. Программа не генерирует электронную подпись и не проверяет её криптографически; она принимает результат внешнего подписания, а окончательную проверку выполняет ГИС МТ.

## Авторизация и чтение

1. В локальном `.env` включить `TRUE_API_ENABLED=true`, при необходимости указать `TRUE_API_INN`. Перезапустить сервер.
2. Открыть экран True API и нажать «Получить запрос авторизации». Программа вызовет `GET /api/v3/true-api/auth/key` на `https://markirovka.sandbox.crptech.ru`.
3. Подписать точную строку `data` присоединённой CMS-подписью тестового сертификата. Сохранить её в base64 без переносов. Не подписывать UUID вместо data, не добавлять пробелы/BOM/перевод строки.
4. Вставить подпись и выполнить авторизацию. Программа отправит UUID и подпись методом `POST /api/v3/true-api/auth/simpleSignIn`. Локальный запрос действует 5 минут и используется один раз.
5. Токен остаётся в памяти серверного процесса и не попадает в `/api/state`, журналы или выгрузку. После перезапуска потребуется авторизация снова. Для ИТ-скрипта допускается локальная переменная окружения `TRUE_API_TOKEN`; не вводите её в командную строку с историей.
6. Запросить сведения о настоящих тестовых КИ методом `POST /api/v3/true-api/cises/info`. По одному КИ на строку, до 100 за запрос в этой версии. Кодировка и служебные символы сохраняются; формат КИ следует взять из актуальной документации товарной группы. Коды `DEMO-*` блокируются.

Наличие ответа не доказывает физического нахождения бутылки в коробе. Полный состав определяет камера. Доступность сведений о нанесении и номере партии нужно подтвердить отдельно. Получение новых кодов СУЗ не реализовано этим адаптером.

## Отправка подписанного документа

Этот этап предназначен для ИТ-специалиста после сверки документации; массовая отправка из учебной очереди недоступна. Все её идентификаторы DEMO, и отправлять их в ГИС МТ нельзя.

Согласовать JSON-схему, `TRUE_API_DOCUMENT_TYPE`, `TRUE_API_PRODUCT_GROUP`, `TRUE_API_DOCUMENT_PATH` и `TRUE_API_STATUS_PATH`. Значения путей в `.env.example` являются исходными настройками транспорта, а не подтверждением доступности конкретного документа для растительных масел. После проверки выставить `TRUE_API_PROFILE_REVIEWED=true`.

Подготовить документ с настоящими тестовыми идентификаторами. Сохранить UTF-8 JSON и создать **откреплённую** CMS-подпись именно над его байтами. Сохранить подпись в base64. Для авторизации нужна присоединённая подпись, для документа — откреплённая; это разные операции.

```powershell
.venv/Scripts/python.exe scripts/true_api_document.py --submit data/document.json --signature data/document.p7s
.venv/Scripts/python.exe scripts/true_api_document.py --status EXTERNAL_DOCUMENT_ID
```

Скрипт использует токен из окружения/.env, а не токен отдельного процесса браузерного демо. Закрытый ключ через скрипт не передаётся. Поле `product_document` формируется base64 от исходных байтов, без пересборки JSON; оболочка содержит `document_format`, `product_document`, `type`, `signature`.

Намерение отправки сохраняется до сетевого вызова. HTTP-ответ с ID означает получение документа, а не окончательное принятие. После тайм-аута или перезапуска в момент отправки повтор блокируется по хешу исходных байтов и профиля; нужно выяснить результат через кабинет/поддержку и не создавать новый JSON с другой расстановкой пробелов ради обхода блокировки. Автоматическое сопоставление статусов конкретного типа документа и исправления принятых агрегатов относятся к следующему этапу интеграции.

## Проверка подключения при получении доступа

Пройти авторизацию; получить сведения о тестовом КИ; отправить один согласованный документ с действительными тестовыми упаковками; подтвердить окончательный статус и состав в кабинете. Затем проверить отказ, истечение токена, отключение сети и тайм-аут отправки. До этого момента интеграция считается подготовленной, но не принятой на стенде ЦРПТ.
